# История изменений

Все значимые правки в коде помечены комментарием `(правка NNN)` — по номеру
можно найти контекст в исходниках. Документ ниже описывает **релизные**
изменения, а не каждую правку.

Формат: [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версии — [SemVer](https://semver.org/lang/ru/).

## [7.1.24] — 2026-11-13

### Английский язык интерфейса — опциональный (правка 955)

- **Что сделано.** Подключены `i18next` + `react-i18next`. В Настройках
  (вкладка «Внешний вид») появился переключатель «Русский / English» —
  действует сразу, без перезапуска. Заводской язык — русский: поведение
  текущих пользователей не меняется. Выбор сохраняется в localStorage
  (`h3-ui-lang`) и дублируется на сервер снимком простых предпочтений,
  поэтому ошибки и статусы API приходят на том же языке, что интерфейс.
- **Объём перевода:** весь UI вкладок, тосты, сообщения API и серверных
  модулей. Не переводятся (по договорённости): раздел «Обучение» и
  справочник промптов, ответы Ассистента, шаблоны воркфлоу и имена нод.
- **Как устроено.** «Естественные ключи»: ключ = исходный русский текст,
  словарь ru пустой (i18next возвращает сам ключ — непропущенная строка
  остаётся русской и ничего не ломает), каталог en — словарь
  русский→английский (`src/lib/i18n/messages/en/*.json`, ~1600 записей).
  Строки вынуты кодомодом по AST (`scripts/i18n-run.mjs` и спутники);
  подписи модульных таблиц оборачиваются в местах вывода. Покрытие
  проверяется аудитом: `npm run i18n:audit` (ключи без перевода и мусор
  каталога — оба нуля). Финальная сверка — автоматическая DOM-пробегка
  (`scratchpad/shot-all.cjs`) по всем вкладкам и настройкам: кириллица в
  интерфейсе не встречается, кроме вкладки «Обучение» и слова «Русский»
  в самом переключателе.
- **Зависимости:** `i18next` + `react-i18next` добавлены в `package.json` и
  лок-файл. Офлайн-бандл установщика npm-пакеты не содержит (зависимости
  ставятся `npm ci` из реестра) — при изменении лок-файла `apply_update.ps1`
  после замены файлов сам запускает окно установки зависимостей.

### Обновление больше не оставляет студию без запуска (правки 956–958)

- **Симптом.** После апдейта приложение не открывалось: пересборка `.next`
  падала, и студия оставалась вообще без сборки интерфейса.
- **Причина.** Установщик считал привезённую сборку устаревшей (в ней не было
  штампа версии), сносил `.next` и запускал `npm run build` на машине юзера.
  А `next build` требует все npm-зависимости — `i18next` и `react-i18next`
  в `node_modules` не доехали (update-zip их не содержит), сборка падала.
- **Что сделано.** `make-update-zip.mjs` пишет в архив `.next\H3_APP_VERSION`:
  установщик видит совпадение версий и готовую сборку не трогает. Перед любой
  пересборкой `install.ps1` сверяет все `dependencies` из `package.json` с
  `node_modules` и доустанавливает недостающее (`npm install` — без сноса
  папки), и только потом удаляет `.next`; при неудаче выбрасывает ошибку,
  сохраняя старую сборку. `apply_update.ps1` перед запуском окна установки
  зависимостей проверяет, что все пакеты из архива реально разрешаются в
  `node_modules`, — если да, апдейт идёт сразу, без переустановки. Когда в
  архиве готовая сборка со штампом текущей версии, окно установки зависимостей
  не открывается вообще.
- **Важно:** фиксы доезжают в составе update-zip: после обновления `.next`
  остаётся со штампом 7.1.24 и не пересобирается.

### Настройки сохраняются, ассистент работает (правка 959)

- **Симптом.** На чистой установке не сохраняются настройки («ошибка
  сохранения»), не отвечает ассистент — и вообще падали запросы к API.
- **Причина.** При переводе серверных сообщений в API-роуты попал клиентский
  хук `useTranslation()` из `react-i18next`. В серверном бандле Next.js
  `react-i18next` не содержит хука — каждый такой роут отвечал HTTP 500
  (`TypeError: (0, f.useTranslation) is not a function`). Задеты были 40
  роутов: `/api/settings`, `/api/llm/chat`, конфиг, модели, генерация и др.
- **Что сделано.** Все серверные роуты переведены на `st()` из
  `src/lib/i18n/server.ts` (тот же словарь, язык из зеркала настроек).
  Добавлена проверка `scripts/check-server-i18n.mjs` — релиз не выпускается,
  если клиентский i18n-хук снова появится в `src/app/api` или `src/lib`.

### Кракозябры в установщике (правка 957)
- **Симптом.** В `setup.exe` 7.1.22 русские тексты наших страниц (страница
  «Готово», подпись галочки) отображались как `Р СѓС‚...`.
- **Причина.** Из `install/installer.nsi` при правке версии выпал UTF-8 BOM,
  и `makensis` прочитал файл как ANSI (в v7.1.21 BOM был).
- **Что сделано.** BOM возвращён; `check-installer.mjs` проверяет BOM и
  валидность UTF-8 у `.nsi` при каждом релизе.

## [7.1.22] — 2026-11-13

### Refine «частями»: раннер больше не зависает на одной задаче (правка 952)

- **Симптом.** У части юзеров Refine «частями» вставал навсегда (и все
  следующие рефайны за ним), хотя общая очередь уже освобождалась.
- **Причина.** Раннер Refine сериализован своим флагом `running` и
  `runTask()`: пока ComfyUI отвечал `running`, цикл опроса крутился вечно.
  Сторож шлюза (правка 950) отпускал ход очереди, но сам раннер про это не
  знал и не переходил к следующей задаче.
- **Что сделано.** В опрос добавлен свой сторож: 30 минут без изменения
  процента у `running`-задачи → честная ошибка «Нет прогресса 30 минут…»,
  задача помечается ошибкой, раннер берёт следующую. Процент берётся из
  того же `/api/comfy/progress`, что и у карточки.
- **Проверено (без GPU):** симуляция `planChunkWindows` + сегментов декода на
  5…1440 кадрах для окон 3/5/8 с — окна и сегменты без дыр/дублей, ни один
  стык окна не попадает в зону кроссфейда, бесконечных циклов нет.

### Refine «частями»: перехлёст нового контента и кроссфейд на стыках окон (правка 953)

- **Причина шва.** Окна не перекрывались НОВЫМ контентом: preserved-голова
  (39 кадров) была только контекстом, новые кадры окна k начинались ровно
  там, где закончилось окно k−1. На 3-секундных окнах нового контента всего
  34 кадра (1.4 с), поэтому граница «новый контент ↔ новый контент» шла
  каждые 1.4 с и читалась как стык.
- **Что сделано.** Preserved-голова укорочена с 12 до 7 токенов (39 → 22
  кадра): окно рефинит ещё 17 кадров, которые уже есть в предыдущем рендере.
  Декод идёт по «дублированному» латенту, а финальная сборка смешивает пару
  кадров (prev → new, маска 0→1 за 17 кадров) и выбрасывает дубли. На выходе
  ровно исходная длина. Аудио-голова окна укорочена соответственно (37 шагов).
- **Сохранённый AV-латент остаётся чистым** (без дублей): для `cfullav`
  по-прежнему собирается вторая, «чистая» цепочка, поэтому lossless-рефайн
  поверх результата не поедет по таймлайну.
- **Попутно исправлено:** короткий хвост последнего сегмента декода больше не
  выбрасывается — предыдущий сегмент растягивается до конца (раньше терялись
  до 17 кадров).
- **Проверено без GPU:** симуляция новой схемы на 5…1440 кадрах × окна 3/5/8 с
  (оба пути — mp4 и latent): дубли не пересекаются, сумма тел+кроссфейдов равна
  исходной длине, сборка сегментов декода точна во всех случаях. Сборка графов
  (202 узла для 10 с / 3 с, 94 для 10 с / 5 с) — 0 битых ссылок и пустых входов.
- **Нужен живой прогон:** это меняет визуальную сборку, проверить на GPU и
  сравнить стыки 3 с / 5 с (до/после). Если понадобится — вынесем в тумблер.

### Генерация: видно, на каком узле идут минуты; зависшая очередь разблокируется; ComfyUI можно перезапустить (правка 950)

- **Симптомы из поддержки.** У части юзеров генерация «висит» на 0% (30 минут —
  2 часа), у части — на 50% «на 3D-апскейлере». Статический аудит всех 11 цепочек
  студии (сборка воркфлоу без GPU) показал: битых ссылок и пустых входов нет,
  модели на месте, стадии прогресса совпадают с сэмплерами. Причина не в
  проводке: на 1080p/длинных клипах dense attention (Sol-Attn по умолчанию
  выключен) идёт минутами за шаг, а карточка показывала только проценты —
  отличить работу от зависания было нельзя.
- **Карточка статуса** теперь показывает текущий узел из `_meta.title`
  воркфлоу («Latent Upscaler (3D) → 1920×1088»), шаг и время на узле. Данные
  берутся из `executingNode` WS-трекера (он и раньше собирался, но в UI не
  доходил) через `/api/comfy/progress`.
- **Лог студии** (`h3-studio-console-*.txt`) получает строки перехода узлов:
  `[stage] 1a2b3c4d → 46:26 «Latent Upscaler (3D) → 1920×1088» [46:21: 42.1s]` —
  по логу сразу видно, где именно идут минуты.
- **«Кадры» (FLF):** подпись Pass 1 больше не «черновик» — «полное разрешение»;
  рядом с выбором режима появилась заметка, что оба прохода идут в целевом
  разрешении (3D-апскейлер пропускается), поэтому это дороже «Текста».
- **«Консоль»:** кнопки «Очистить очередь» (interrupt + удаление pending через
  существующий `/api/comfy/purge-queue`) и «Перезапустить ComfyUI» (Electron
  убивает дерево процессов ComfyUI и поднимает заново, ожидая `/system_stats`).
- **Сторож очереди** в `comfy-turn`: жёсткие 6 часов заменены на 30 минут **без
  прогресса** — любое обновление прогресса/сообщения перезапускает отсчёт, так
  что долгая живая генерация не снимается, а залипшая освобождает очередь.
  Сама задача в ComfyUI при этом не отменяется.
- **Проверки:** `tsc --noEmit` — 0; `node --check` для `electron/main.js` и
  `electron/preload.js`; статический аудит воркфлоу — 11 цепочек, 0 проблем.

### Изображение: официальная image-модель H3 распознаётся и считается (правка 949)

- **Симптом.** После починки VAE генерация падала ещё до сэмплинга:
  `ERROR UNSUPPORTED DIFFUSION MODEL … ERROR: Could not detect model type of:
  models\diffusion_models\minimax_h3_image_pruned_w4a8.safetensors`.
- **Причина.** Ядро 0.44.0 знает только H3-видео (AV-поток): детектор искал
  `audio_patch_proj`, которого у официальной image-модели нет, а класса
  `MiniMaxH3Image` (один латент-поток, своя сетка PDD-сигм) в 0.44 тоже не было.
- **Патчи ядра.** `comfy/ldm/minimax/model.py` — `MiniMaxH3ImageModel`,
  необязательный аудио-поток, `pdd_grid`; `comfy/model_base.py` —
  `MiniMaxH3Image` с `ModelType.FLOW` и `MiniMaxH3ImageModelSampling`;
  `comfy/supported_models.py` — класс и регистрация; `comfy/model_detection.py` —
  image-чекпоинт по отсутствию `audio_patch_proj`. Класс сэмплинга лежит в
  `model.py`, а не отдельным `sampling.py`: установщик сверяет, что каждый патч
  уже существует в ядре, новый файл ядра он бы не принял.
- **Воркфлоу.** Официальная image-модель однопоточная, а `PH3ImageConditioning`
  отдаёт AV-латент: в сэмплер идёт только видео-часть (`LTXVSeparateAVLatent`
  до сэмплера), `VAEDecode` берёт выход сэмплера. Второй проход больше не
  использует `H3InjectVideoLatent` (ему нужен AV-латент) — база входит обычным
  `VAEEncode`. `MiniMaxH3SigmaShift` из image-графа убран: он подменял сетку
  PDD-сигм чекпоинта на `ModelSamplingAV`.
- **Проверено:** чекпоинт детектится как `minimax_h3_image`, 1378/1378 ключей
  совпадают, все веса конечные, forward в bf16 отдаёт корректный латент
  (H3 поддерживает bf16, не fp16 — это уже штатный выбор ядра).

### Изображение: официальный image-VAE грузится, подписи вкладки читаются (правки 946, 947)

- **Симптом.** Любая генерация во вкладке «Изображение» падала с
  `RuntimeError: Error(s) in loading state_dict for PH3ImageVAE`:
  `post_quant_conv` 1×1×1 против 1×1 из файла, `register_tokens` 2048 против 1024,
  `norm_out` 2048 против 1024 и ещё сотня таких же строк.
- **Причина.** Ядро ComfyUI 0.44 знает только VAE p-h3-image (32 головы, 3D-conv):
  на `decoder.proj_out.weight.shape[0] == 768` оно всегда собирало `PH3ImageVAE`.
  Официальный `minimax_h3_image_vae_fp16` из Comfy-Org/MiniMax-H3-Image — другой
  декодер: 16 голов, 2D-rope и 2D `post_quant_conv`.
- **Что сделано.** В `install/comfy-patches` добавлены `comfy/ldm/minimax/vae.py`
  и `comfy/sd.py` с классом `MiniMaxH3ImageVAE`; загрузчик различает варианты по
  ширине `decoder.x_embedder` (1024 — official, 2048 — p-h3-image). Как и прочие
  патчи ядра, это доезжает через апдейт-зип и применяется при первом запуске
  ComfyUI (`syncCorePatches`) — переустановка не нужна.
- **Текст вкладки.** `src/lib/comfy/image-template.ts` был сохранён двойной
  кодировкой (UTF-8 → CP1251): 190 строк подписей («4 шага — быстрый прогон»,
  «4 МП · 2048×2048», «Один проход: детальность растёт…») показывались
  кракозябрами. Текст восстановлен обратным преобразованием.
- **Проверка:** `npm run check:comfy-sync` — новые пункты про оба патча ядра и про
  отсутствие двойной кодировки (88 проверок).

### Установка: обрыв замены ядра больше не съедает модели; битая нода не блокирует студию (правка 945)

- **Что терялось.** Замена ядра ComfyUI (шаг 4) сделана в три хода: данные
  (`models`, `custom_nodes`, `user`, `output`, `input`, `temp`,
  `extra_model_paths.yaml`, `comfy.settings.json`, в плоской раскладке ещё
  `python_embeded`) → `ComfyUI.keep`, старое ядро → `ComfyUI.old`, новое ядро →
  на место. Если установка обрывалась между этими шагами (Ctrl-C, крестик окна,
  перезагрузка), следующий запуск **удалял `ComfyUI.keep` вместе со всеми
  моделями пользователя** — проверка «ядро уже на месте» просто не доходила до
  возврата данных.
- **Что сделано.** Перед проверкой ядра работает восстановление: `ComfyUI.old`
  возвращается на место, если новое ядро так и не разложили (и удаляется, если
  новое уже на месте), затем содержимое `ComfyUI.keep` сливается обратно в ядро.
  Слияние рекурсивное (`Move-MergeInto`): пустые `models\*`, которые ComfyUI
  успел создать сам, не ломают перенос и ничего не затирают. То же используется
  при откате неудачной распаковки. Молча удалить непустой `ComfyUI.keep` теперь
  нельзя — он либо возвращается, либо уводится в `ComfyUI.keep.old-<дата>` с
  предупреждением.
- **Одна недоступная нода больше не ломает студию.** В шаге 6 ошибка
  скачивания/распаковки архива была `Fail`, то есть `exit 1`, а Electron на
  ненулевом коде не поднимает ComfyUI — пользователь оставался без студии из-за
  одного архива с GitHub (прокси, лимит, обрыв). Теперь это предупреждение с
  подсказкой «повторный install.bat доставит ноду», а если не встала ни одна
  внешняя нода — отдельное предупреждение про сеть/прокси.
- **Самодиагностика** (`diagnostics.bat`) теперь видит брошенные
  `ComfyUI.keep`/`ComfyUI.old`/`ComfyUI.keep.old-*` рядом с корнем и говорит, как

### Вкладка «Изображение»: двухпроходная генерация (правка 935)

- В панели параметров появился выбор «Проходы»: **один**, **два — детали поверх

  обычный img2img: картинка первого прохода декодируется, при необходимости
  растягивается до целевого размера (`ImageScale`, lanczos), кодируется

  пака `ComfyUI-H3-FaceRefine`, он в `install/nodes.json`, то есть есть у всех),
  после чего `SamplerCustomAdvanced` доходит его снизу сетки сигм.
- Сила и длина второго прохода настраиваются явно: «Сила 2-го прохода»
  (`denoise`, 0.05…0.8, по умолчанию 0.35) и «Шаги 2-го прохода» (1…12,
  по умолчанию 4). Сигмы считает `BasicScheduler` (`simple`) — тот же приём,
  что в Tile Upscale и Face Refine: он берёт нижний хвост полной сетки,

  кадр, см. docstring `H3InjectVideoLatent`).
- «Уточнение для 2-го прохода» — вторая строка к запросу только для второго
  прохода (апсемплер при этом не перезапускается): можно первый проход оставить

### Ассистент: замена референсов посреди чата (правка 906)

- **Ассистент больше не может принять старое описание за новый референс.**
  Описания референсов кэшируются по содержимому файла, но у кэша есть резервный
  индекс «имя файла → последнее описание» для случаев, когда дайджест не удался
  (нет mmproj, таймаут, LLM занят, исчерпан 7-минутный бюджет). Индекс не
  проверял содержимое: после замены рефа с тем же именем (типично — после
  «чистки input», смены папки бэкенда или перезалива файла) модель получала
  описание **старого** файла, а сырое изображение при этом не прикреплялось —
  то есть не могла увидеть новое. Теперь в индексе хранится отпечаток
  содержимого (размер + хэш), и описание принимается только при совпадении;
  устаревшее отбрасывается, и маршрут уходит в честный путь «файл приложен
  напрямую» или «не вижу, mmproj нет».
- **Модель получает явное предупреждение «РЕФЕРЕНСЫ ИЗМЕНИЛИСЬ».** Метка
  `<Picture N>` — это позиция в списке, а не идентификатор файла: после замены
  рефа (UI делает «убрать» + добавить, новый файл встаёт в конец) тот же номер
  начинает означать ДРУГОЙ файл, а в истории чата остаются реплики ассистента
  про прежний. Чат теперь хранит отпечаток набора, который модель реально
  видела, и при расхождении в системный промпт добавляется блок с диффом
  (что изменено / появилось / убрано) и правилом: не переносить описания из
  прошлых реплик и уточнять, о каком референсе речь, если пользователь
  ссылается на «второй» по смыслу старого файла.
- **Системный промпт и payload собираются из ОДНОГО снимка референсов.**
  Раньше промпт пересобирал список сам уже после `await fetch('/api/config')`
  (до 5 с) — если пользователь в это окно менял рефы, промпт перечислял новый
  набор, а файлы прикреплялись старые (тот же класс бага, что закрывала
  правка 823).
- **Отпечаток больших файлов (видео) стал надёжнее.** Раньше хэшировались
  только начало и конец файла: два разных ролика одного размера с совпадающими
  краями получали ОДИН ключ кэша, и модель описывала чужое видео. Теперь 4
  пробы по диагонали файла (начало, 1/3, 2/3, конец) со смещениями в хэше.
  Побочный эффект: у видео >16 МБ описания один раз пересоздадутся.
- **Индекс описаний ограничен 400 записями** (раньше рос бесконечно — по
  записи на каждое когда-либо описанное имя файла).
- Проверено без GPU/LLM: `scratchpad/assistant-ref-replace-check.mjs` —

### Монтажка: перенос с упором в соседа, удаление без сдвига, мультивыбор клипов (правка 899)

- **Упор вместо выталкивания.** При перетаскивании клипа базовой дорожки соседи
  не раздвигаются и не меняются местами: клип скользит по шкале и упирается в
  соседний клип, дальше не идёт. Встык ставится ровно встык; порядок клипов при
  перетаскивании не меняется.
- **Удаление без ripple.** Удалённый клип оставляет пустое место — следующие клипы
  не сдвигаются влево, освободившаяся пауза передаётся следующему по позиции клипу.
- **Мультивыбор.** Ctrl/Cmd/Shift+клик добавляет или снимает клип (база, слой,
  аудио); выделенная группа перемещается синхронно (по дорожке и между дорожек),
  удаляется всей группой (Delete) и подсвечивается на таймлайне.

### Монтажка: дисперсия в превью и в рендере теперь одинаковая (правка 898)

- **Сила дисперсии пересчитана в доли кадра.** Раньше превью смещало каналы на
  фиксированное число экранных пикселей, а финальный рендер — на долю кадра,
  из-за чего в готовом файле дисперсия выглядела в несколько раз сильнее.
  Теперь превью/calibration считаются по тем же коэффициентам, что и ffmpeg
  (общая формула в `src/lib/montage-dispersion.ts`), и не зависят от размера
  окна и масштаба превью.
- **Профиль смещений совпадает с рендером** (закон линзы k1·r² + k2·r⁴,
  нормированный по полудиагонали): у центра смещение почти нулевое, максимум
  в углах. Отдельная «маска чистого центра» в превью убрана — её роль играет
  сам профиль; ползунок маски центра теперь одинаково приглушает силу и в
  превью, и в рендере.

### Исправления (правка 815)

- **Отдельная sigma-лестница Pass 2 при выключенном 3D-апскейлере.** Штатная
  лестница pass 2 начинается с sigma ≈ 0.90–0.95, а у H3 (тип FLOW_AV, `CONST`)
  вход сэмплера = `sigma·шум + (1−sigma)·латент` — то есть ~90 % латента
  pass 1 затиралось свежим шумом и pass 2 генерировал почти заново. Для
  латента от 3D-апскейлера это рассчитано, но bislerp-растянутый латент
  (правка 811) вне обучающего распределения — за 3 шага шум не разглаживался
  и оставался как «паутинка/перхоть». При обходе 3D-апскейлера теперь
  используется своя лестница `BYPASS_SIGMA_VARIANTS`. Эксперименты: v1
  (старт 0.50) и v2 (0.70) дали сетку латентных патчей — мало перерисовки;
  итоговая v3 — наоборот горячее штатной: старты 0.95–0.98 (но <1.0, иначе
  вклад латента pass 1 обнуляется). Все варианты 3–7 step; в main-цепочке
  и в extend-клипах.

### Исправления (правка 810)

- **1080p в «полном» режиме без 3D-апскейлера больше не «мылит» и не двоит.**

### Face Refine (правка 722)

- **Новая вкладка «Face Refine»** — перерисовка мелких лиц в готовом ролике.
  H3 плохо рисует лицо, когда голова занимает малую долю кадра, и это свойство
  кадра, а не разрешения (на 720p и выше проблема остаётся). Нода находит лицо
  покадрово, кропит его так, чтобы оно занимало ~40 % холста, перегенерирует
  крупно с низким denoise и вклеивает обратно **только область лица**
  (feather + колор-матч). Остальной кадр остаётся исходным.
  Используется набор нод `ComfyUI-H3-FaceRefine` (Carasibana, MIT) — он уже
  стоял в `custom_nodes/`, но был нерабочим: не было детектора и
  python-пакетов. Установлены `ultralytics`, `scenedetect`, `insightface`
  (torch не тронут) и скачаны `face_yolov8m.pt` + `person_yolov8m-seg.pt`.
- **Кого именно перерисовывать** — три способа:
  * правило + номер в рейтинге (`Самое крупное лицо`, `Ближе к центру кадра`,
    `Самое левое/правое/верхнее/нижнее`, `Самое мелкое`, `Самое уверенное`);
  * **клик по лицу в кадре исходника** (правка 723) — окно с превью ролика,
    прокруткой по кадрам и точкой на нужном лице: трекер берёт ближайшее к
    точке лицо и ведёт этого человека через весь ролик. Правила видят только
    геометрию кадра, поэтому в толпе и на общих планах выбор «залипал» на одном
    и том же лице, а точка задаёт цель напрямую. Координаты считаются в
    пикселях самого видео, номер кадра — по fps из `ffprobe` (элемент `<video>`
    кадров не отдаёт), так что клик попадает в тот кадр, на котором сделан.
    **Точка главнее референс-фото:** при подключённом `identity_reference` нода
    вообще не смотрит на X/Y (в отчёте — «ignored - identity_reference
    decides») и ведёт того, кто совпал с фото, — поэтому, пока лицо выбрано
    кликом, фото в воркфлоу не подаётся, а в метаданных остаётся пометка
    `identity_reference_ignored`;
  * **референс-фото конкретного человека** — трекер сопоставляет лица по
    эмбеддингу (insightface, `buffalo_l` скачивается сам при первом запуске) и
    ведёт этого человека через весь ролик, даже если нумерация лиц сбилась.
- **Промпт и референсы берутся из сайдкара исходника** — Face Refine должен
  перерисовывать лицо в той же сцене, поэтому сцена и персонажи те же.
  Свой промпт можно задать вручную.
- Параметры под наше железо: канва 512 (дешевле 768 в 2.25× по latent-токенам),
  4 шага (наша модель 4-шаговая), базовый denoise 0.35. Денойз из SDXL-семейства
  не переносится: H3 — flow matching со сдвигом 12, denoise 0.25 → эффективная
  sigma 0.800 (кадр переписывается целиком).
- **Денойз масштабируется по размеру лица** в кадре: мелкие лица получают
  полную силу, крупные — множитель 0.35 (у них уже есть детали).
- **Живое превью генерации** — как на вкладках «Генерация», «Refine» и
  «Tile Upscale»: KJ-нода `ModelPreviewOverrideKJ` в model-цепочке шлёт кадр на
  каждом шаге сэмплинга, статус внизу показывает его через
  `/api/comfy/preview`. Стандартные превью в этой сборке отключены
  (`--preview-method NoPreviews`), без KJ-ноды окно оставалось пустым.
- **«Далёкие планы» — детектор человека** (`fallback_detector`). На кадрах, где
  лица не видно (человек спиной, в капюшоне), трекер берёт бокс
  `person_yolov8m-seg` и считает головой его верх — это точнее, чем
  интерполировать между соседними найденными лицами. Папку детекторов студия
  теперь регистрирует сама (`extra_model_paths.yaml` → категория `ultralytics`
  → `models/ultralytics`), иначе нода видела только дефолтный
  `face_yolov8m.pt`; значения комбо резолвятся по `/object_info`, чтобы имена с
  подпапкой (`bbox/face_yolov8m.pt`) совпадали со списком бэкенда.
- Результат — обычное видео в общей галерее, с бейджем «Face Refine»
  (салатовая метка; сама вкладка — жёлтая) и полными метаданными
  (canvas/denoise/steps/правило выбора/сид/источник/время).

### Известные ограничения

- Требуется NVIDIA GPU (12+ ГБ VRAM рекомендуется, минимум 8 ГБ) и
  драйвер CUDA 12.x.
- Live-режим (real-time / HLS) в студию **не входит**: это отдельный
  инструмент (свой HLS-сервер и плеер), а не обработка файла. Вкладка
  «Upscale» работает только с готовыми видеофайлами.
- ESLint в проекте не используется; проверка качества — `npm run typecheck`.
